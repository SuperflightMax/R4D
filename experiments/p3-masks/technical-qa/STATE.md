## Что нужно получить от Builder/Lead одним frozen-пакетом

1. Идентификатор кандидата, один source commit и точный путь/версию build;
   полный список relative paths, sizes и SHA256 всех доставляемых файлов
   (включая config/manifest/projection, runtime, masks, ball/shadow, notices).
   VQA получает эти же bytes. Новое содержимое означает нового кандидата.
2. Закреплённые recipe/toolchain/lockfile для связи source → build и native
   commit → compiled runtime; указатели на использованные входы. Приватные
   TS, source maps, абсолютные private source paths и credentials не входят
   в публичный bundle. Для локальной независимой сверки допускается только
   авторизованный native source из поручения.
3. Как запустить статический bundle под `/review/r4d/p3-masks/`; способы
   получить seed/start/config/core identity, точный tick и состояние,
   управлять pause/+tick/seek, экспортировать и импортировать JSON.
   Подходит существующий внутренний QA-механизм, отдельная панель не нужна.
   Указать, экспортирует ли checkpoint состояние или восстанавливает его
   из seed+tick, и как трактуются начальный/конечный ticks.
4. Короткие сведения о собственных масках/anchors/depth/alpha и известных
   ограничениях кандидата. Это контекст проверки, не замена независимой QA.

## Необходимый порядок проверки после freeze — пока только план

1. **Идентичность.** Сверить source commit и фактические file hashes;
   проверить происхождение compiled native по закреплённому recipe.
   Сравнить весь config с exact P1 (разрешено только rng.seed для нового
   запуска), projection/manifest/domains и source bytes. Согласовать с VQA
   один candidate ID и набор хешей. Текущий branch HEAD не заменяет freeze.
2. **Обычные запуски и replay.** Сохранить первые три обычных новых запуска
   без отбрасывания неудобных исходов. Два различных seed должны реально
   различать траектории. Для тех же seed/start/config сравнить фиксированные
   ticks, позиции/скорости, столкновения и конечный результат с независимым
   прогоном exact native; не считать отчёт Builder независимым доказательством.
   Проверить повтор того же запуска. Декоративный рендер и Art/Geometry,
   масштаб и доступная смена вида не должны менять native-последовательность
   или расходовать её PRNG; сравнивать при одинаковых ticks, не wall time.
3. **Управление временем и JSON.** Pause удерживает точный tick; +1/+несколько
   шагов и seek вперёд/назад дают те же native-состояния, что прямой прогон.
   После export/import в свежей загрузке совпадают версия/seed/start/config,
   выбранный tick, состояние и дальнейшие шаги. Проверить участок контакта
   и завершение, real-time и пошаговый режим на одной последовательности.
4. **Диагностика вместе с VQA.** Проверить четыре сочетания Art/Geometry:
   реальные контуры из config выше арта, незалитые и контрастные; выключение
   Art снимает невидимые маски с диагностического шарика/пути. На обычных
   seeds смотреть до/во время/после контакта и смены порядка, частичное
   перекрытие, боковые отскоки, борта и вход в корзину. Baked shadow не
   становится непрозрачным телом. Визуальное качество оценивается по кадрам
   и движению; одни координаты, HTTP 200 или build его не доказывают.
5. **Статическая загрузка.** Открыть frozen bundle по нужному вложенному
   route и повторить свежую загрузку: локальные relative assets/module paths,
   без отсутствующих ресурсов, незаявленного backend/POST и ошибок запуска.
   Проверить доставляемые bytes и отсутствие приватных TS/source maps/paths,
   а не только успешный ответ index.html. Серверной публикации это не разрешает.

Для найденных хороших и плохих воспроизведений сохранить минимальный
checkpoint с candidate/file identity, seed, start/config/core/projection
версией, tick, наблюдением и результатом. Число обычных запусков увеличивать
только для конкретного непроверенного сценария, без охоты за красивым seed.
Дефекты общего маппинга записывать отдельно от дефектов реализации/среды/
самой проверки; коллайдеры не подгонять. Связанные замечания возвращать
одним пакетом. Кандидат самостоятельно не исправляется. PASS возможен
только для фактически проверенных свойств названной версии.
