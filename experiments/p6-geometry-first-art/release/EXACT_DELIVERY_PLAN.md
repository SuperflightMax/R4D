## Manifest и приватная передача кандидата

`PUBLIC_MANIFEST.template.json` задаёт состав будущего публичного `manifest.json`. Это шаблон: null, пустые списки файлов и статус `template` не считаются готовым кандидатом. Фактические start/config/projection берутся из принятого входа без изменения; их точные хеши фиксируются в заполненном manifest вместе с общими динамическими параметрами.

`CANDIDATE_HANDOFF.template.json` задаёт приватную передачу Lead/CTO. Она хранит source commit, хеш публичного manifest, точный список файлов, имя/размер/SHA-256 окончательного архива, ссылки на QA и источник wrapping. Архив и приватная передача размещаются только в own E runtime. Точный формат архива выбирается по существующей wrapping; новый pipeline не создаётся.

Файлы в `manifest.json.files` перечисляются в лексикографическом порядке, пути относительны публичному корню, разделитель `/`. Запрещены абсолютные/UNC/drive paths, `.`/`..`, backslash, повторные пути, коллизии регистра Windows, ссылки и reparse points. `manifest.json` не включает собственный хеш в свой список: его хеш хранит внешняя приватная передача. Архив не содержит приватную передачу. Версия Git закрепляет исходник, SHA-256 закрепляет точные доставляемые байты.

Для точной сериализации `artifactInventory` содержит те же файлы, что `manifest.json.files`, без самого manifest; каждая запись имеет только ключи `path`, `bytes`, `sha256` именно в этом порядке. Сортировка пути — ordinal, SHA-256 записывается lowercase hex. `artifactInventorySha256` вычисляется по UTF-8 без BOM от компактного JSON массива без отступов и пробелов между токенами, с одним LF в конце; строки экранируются по правилам `JSON.stringify`. QA указывает хеш этой же последовательности. Manifest и приватная передача сохраняются в UTF-8 без BOM с LF; после фиксации их байты не пересериализуются. Полный состав архива равен inventory плюс `manifest.json`.

## Замораживание и точная доставка

1. Получить совпадающие source/output/QA, все provenance/license данные и pin чистой wrapping. Проверить scope и ресурсы до тяжёлой операции.
2. Создать собственную candidate область в own runtime, скопировать только перечисленные готовые файлы и выполнить локальные проверки. Не собирать из незаявленного HEAD и не выбирать удачные seed для выпуска.
3. Записать публичный manifest, вычислить его SHA-256, сформировать окончательный архив по wrapping, вычислить его bytes/SHA-256 и заполнить приватную передачу. Повторно перечислить файлы и сверить хеши. Это и есть immutable candidate; любое изменение создаёт новый candidate ID и архив с новыми хешами.
4. Передать Lead конкретный candidate ID, source commit, manifest SHA-256, archive bytes/SHA-256, вывод приватности/лицензий, соответствующую QA и точный target path. Token в файлы репозитория и публичный manifest не сохраняется.
5. Дождаться отдельного сериализованного exact окна CTO после P3. Поручение CTO должно однозначно назвать тот же candidate/архив/хеш, адрес назначения, target path, pin wrapping, разрешённые операции и применимый способ возврата к предыдущей версии. Из общего Stage 2 это разрешение не выводится.
6. В разрешённом окне перед записью ещё раз сверить все байты с разрешённым архивом. Применить существующую wrapping только к указанному target; не менять общий Review, доступ, маршруты других опытов и серверную конфигурацию сверх точного поручения. Не пересобирать и не исправлять пакет во время доставки.
7. Проверить связь опубликованной версии с candidate и доступность нужного просмотра в объёме разрешённого smoke. Сообщить точный URL, candidate/source/хеши, фактические проверки и ограничения. При неуспехе классифицировать причину; rollback или дополнительные серверные действия выполнять только в пределах поручения CTO.

Без pin wrapping нельзя назначить команды, архивный формат и серверные пути. Сейчас запросов к серверу, SSH-аудита, staging, nginx, deploy и получения token нет; эти значения остаются незаполненными во внешней передаче до адресного разрешения.
