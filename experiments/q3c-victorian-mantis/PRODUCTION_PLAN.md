Задания для ближайшей сборки. Пути приведены относительно `experiments/q3c-victorian-mantis/`.

- **Concept · `design/concept-stage-d/**`.** Дай Asset и Builder один рабочий ориентир по масштабу и силуэту механического мотылька рядом с раскрытым богомолом. Укажи ритм взмахов, читаемую подготовку броска и короткий рисунок вспышки, стружки и пыли в точке захвата. Передай ориентиры сразу, чтобы художник и Builder могли работать параллельно.
- **Asset · `assets/production-stage-d/**`.** Передай пригодные для анимации корпус мотылька и отдельные крылья с точками крепления, а также компактный набор латунных обломков, искр и пыли в стиле C2. В этой же области укажи имена файлов, масштаб и pivots. Первую рабочую версию мотылька передай Builder до готовности всего набора эффектов.
- **Builder · `src/**`, `tests/**`, `index.html`, `package.json`, `package-lock.json`, `vite.config.js`, при необходимости `public/**`.** Единственный runtime writer. Начни с принятого C2 и текущего `?seed=`. Добавь ходьбу с постановкой лап и переносом веса, наведение взгляда, полёт мотылька после раскрытия и один цикл охоты по действию пользователя. Безопасная точка появления выбирается случайно в видимой области и воспроизводится с seed. При недосягаемой цели движение сближает её с богомолом. Захват происходит при контакте клешней с мотыльком, а рассыпание начинается в мировой точке удара. После реакции герой возвращается к живому idle. «Ещё мотылёк» повторяет охоту без перезагрузки, «Заново» повторяет всю историю. Свяжи основные действия мышью, клавиатурой и касанием. Интегрируй готовые части по мере передачи и передай Lead точный SHA, команды запуска, URL и наблюдаемые ограничения.

Работа параллельная. Каждый автор передаёт конкретный путь и версию. Git commits проходят по готовности по одному, с точным списком staged-файлов. Кандидат для показа закрепляет версии использованных материалов и runtime в одном SHA. Первый результат для Lead — рабочий проход всей истории с захватом и повтором.

**Проверка перед показом `WHOLE_DEMO`.** `npm test` и `npm run build` проходят на версии для показа. Обычный smoke 1× на desktop и узком mobile охватывает путь от первого ввода до повторной охоты и перезапуска. Основные действия проверяются мышью, клавиатурой и касанием. Фиксированный seed с тем же вводом воспроизводит появление и траекторию. Обычные прогоны дают безопасные случайные точки появления. При захвате виден фактический контакт, и частицы выходят из точки удара. Runtime и консоль проходят без ошибок. Кандидат передаётся с наблюдаемыми ограничениями и их влиянием на показ.

Этого объёма достаточно для показа демонстрации. Вопрос полной независимой release QA рассматривается отдельно при решении о релизе. Точечная помощь существующих QA подключается по конкретной проблеме без ожидания всей матрицы.

**A. Внутренний visual/mechanical anchor.** Concept Artist задаёт цельный дорогой викторианский образ той же конструкции в capsule/mantis и красивых промежуточных позах: читаемые массы, хватательные конечности, видимые люки/посадочные места, шарниры, непрерывность связанных деталей и направление ритма. Это рабочая опора художников и Builder, не конкурс других существ и не новый внешний gate для Max. Передача через Lead с точными путями/версией; неизвестные, требующие совместного решения, обсуждаются рано.

**B. Ранний живой vertical slice.** Builder начинает минимальную связную сцену первого ввода, маячка, весомого падения на него и настоящего последовательного выхода лап/глаза через люки. Внешний вид и механика рано соединяются с A, чтобы расхождение не обнаружилось только после полной сборки. Технический каркас допустим как промежуточная работа, но не засчитывается художественным результатом. Asset Artist поставляет первые согласованные части без ожидания полного набора. В runtime пишет только Builder.

**C. Цельный asset/rig pass.** Asset Artist развивает ту же конструкцию в согласованный набор деталей, материалов и перекрытий. Через Lead передаёт Builder фиксированную версию с назначением частей, pivots/посадками и необходимыми зонами перекрытия. Builder собирает непрерывную capsule→высокий mantis трансформацию и проверяет рискованные взаимодействия на реальной геометрии. Выбранная реализация и инструменты — его профессиональная ответственность в границах заказа. Отдельные красивые картинки не заменяют пригодные для рига детали и работающие переходы.

**D. Цельная демонстрация.** Живой idle обеих форм и индивидуальная нелинейная кинематика из C2 входят в общую сцену. Текущие задания и объём проверки перед показом приведены выше.

**E. Отдельное решение о релизе.** После показа CTO определяет, нужен ли релиз и какой объём независимой проверки для него требуется. Полный заказ принимается по канонической карточке.

## Безопасное соединение работ в общем checkout

1. Каждый пишет только свою область из STATE; не создаёт clone/worktree, subagents или второго координатора. Общие project/package файлы вне каталога Q3C не меняются без отдельного решения CTO.
2. Каждая передача называет точный путь, версию материала/candidate, сделанное и оставшееся. Lead фиксирует существенную передачу в STATE, сохраняя отличие задания от факта его получения.
3. Художественные материалы передаются через Lead. Builder читает их и один меняет runtime; изменение авторского asset запрашивается его владельцу, либо Lead явно передаёт владение конкретным файлом.
4. QA получают неизменяемый для текущего просмотра candidate/commit и способ запуска. Следующая runtime-коррекция начинается после фиксации проверенной версии; результаты не приписываются другой сборке.
5. Git index общий. Owner commits этой поставки, C1, QA follow-ups и release report доставлены последовательно в согласованных слотах. Для следующих согласованных работ сохраняются exact paths и сериализация Git; QA commits относятся только к их QA-областям по выдаче Lead/CTO. Lead не правит авторский runtime/product source. Во время чужой Git-операции не выполнять конкурирующую запись index/commit. Чужой staged/WIP не присваивать, не сбрасывать и не прятать.
6. Доставку подтверждает commit SHA и push, запуск задания — фактический task turn ID, готовность поведения — наблюдение на работающем candidate. Эти факты не заменяют друг друга.

## Оценка и управление отклонениями

Lead сверяет продвижение по рабочим версиям. Первый контроль Stage D — проход до реального захвата и повторной охоты. При повторе без прогресса Lead передаёт CTO конкретное препятствие, проверенную версию и варианты продолжения. Ограничения показа фиксируются отдельно от требований карточки заказа.
