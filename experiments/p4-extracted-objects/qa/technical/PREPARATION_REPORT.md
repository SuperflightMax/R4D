## Семантика, которую важно сохранить в consumer

Изученный native `step`: cap скорости до интеграции → gravity → position →
pins в исходном порядке → segments в исходном порядке → implicit walls →
near-miss → quantize → сохранить RNG → увеличить tick → bucket/bottom.
Новая физика, пересортировка объектов и отдельная траектория для просмотра
не нужны. Нет отдельной высоты или фазы физического «погружения».

Контакт требует проникновения и входящей нормальной скорости для отражения
и события. Геометрическое выталкивание само по себе не доказывает нового
отражения. Для pin/segment/wall `object_hit.tick` относится к входному
состоянию: например, первый контакт seed1 имеет event tick94, а состояние
после него — tick95. `bucket_entered` имеет уже новый tick (seed4: 2088).

Корзина проверяется после quantize по строгому `centerDistance < bucket.r`.
Радиус шара не вычитается из радиуса корзины. На входе сразу выставляются
`done/result`; физического опускания до полного скрытия шара нет. Открытый
низ завершает run только при `ball.pos.y - ball.r > board.height`.
Ограничение 16 секунд применяет `runUntilDone` через maxTicks=3200 и
`timeoutSimRunSession`; сам один вызов `stepSimRunSession` таймаут не
выставляет. В обычной серии таймаут не встретился.

## Наблюдаемые данные для Builder

Нужен небольшой внутренний доступ к состоянию и действиям; новые элементы
главного интерфейса из этого отчёта не следуют. Названия hooks свободны.

- Снимок полного native состояния без форматирования координат: `tick`,
  `rngU32`, `ball.pos`, `ball.vel`, `nearMissBucketIds`, `done`, `result`.
  Также actual config, dropId, core/config/projection/art версии и SHA.
  Возвращать копию, чтобы чтение QA не меняло живое состояние.
- Пауза, продвижение на N физических тиков, replay и seek на заданный tick.
  Пауза должна показывать точное состояние выбранного тика. В конечном
  состоянии дополнительные шаги не двигают шар. Seek сохраняет все
  обязательные поля, включая PRNG; воспроизведение от исходного seed
  штатными шагами достаточно.
- Экспорт/импорт воспроизводимого run: версия схемы, seed, drop/start,
  actual config (с исходным содержимым кроме seed), версии/хеши core,
  геометрии и проекции; выбранный tick и полный snapshot для проверки.
  Art/view/zoom/geometry могут быть отдельными полями представления и не
  должны менять физические поля или расходовать native PRNG.
- После импорта нужны наблюдаемые ошибки несовместимого/повреждённого
  ввода, без скрытого продолжения с другим config или seed. Успешный импорт
  должен позволять точный повтор и сверку checkpoint. Фактическую схему
  consumer проверю после freeze; `replay-records.json` в runtime — fixture
  oracle, а не предписанная продуктовая схема.
- Желательна наблюдаемая готовность арта и сообщения об ошибках загрузки,
  чтобы проверять реальный consumer и cold loading, а не кадр до окончания
  загрузки. Private paths/TS/maps/source не должны попадать в публикацию
  или экспорт. Эти свойства пока не проверены на P4.

## Evidence, воспроизведение и продолжение

- `scripts/prepare-oracle.mjs`: получает exact inputs из Git и проверяет
  JPG. Аргументы: public repo, разрешённая native repo, read-only JPG,
  собственный runtime output directory. Не записывает в источники.
- `scripts/run-oracle.mjs <prepared-runtime-directory>`: исполняет
  неизменённое native ядро, без зависимостей npm и без нового симулятора.
- `evidence/oracle-checks.json`: шесть завершённых проверок.
- `evidence/ordinary-runs.json`: все результаты, trajectory/physical hashes
  и checkpoints. State hashes используют JSON порядка полей oracle;
  потребитель сравнивается по полям/числам, а не порядку ключей JSON.
- `evidence/diagnostic-terminal-states.json`: отдельно помеченные
  диагностические состояния.

Полные JSONL trajectories, fixtures replay и private native bytes остаются
в собственном runtime `oracle-01/`, не в Git. Тяжёлые временные файлы,
кэши и outputs направляются только туда через process-local окружение.
Новые пакеты, браузер, сервер и генерация арта не требовались. Перед
подготовкой: RAM свободно 17.86/31.91 GiB, CPU 10%/24 logical,
