# R4D → архитектор: FX Workshop — ревью и подготовка этапа 1

**Дата:** 19 ноября 2026. **Источник:** актуальные решения Макса через Product Lead ArtFoldi.
**Статус:** **ARCHITECTURE REVIEW REQUESTED / NO IMPLEMENTATION GO**.

**Полная продуктовая постановка:** [FX Workshop — актуальный бриф](../../docs/2026-11-19-fx-workshop-product-brief.md). Читать **целиком**, включая долгосрочные сценарии, четыре продуктовых этапа, явный запрос на составные конструкторы **трейлов и сложных партиклов**, и запреты на overengineering. Этот короткий документ не заменяет бриф.

## Почему можно брать на ревью сейчас

Макс поставил условие: сначала архитектор готовит карточку ART-UI (либо запускает его по разрешению), только потом разбирает FX. Карточка ART-UI уже подготовлена в [orders/art-ui/ART-UI-ATLAS.md](../../orders/art-ui/ART-UI-ATLAS.md), **HOLD**. Условие для **архитектурного разбора** FX Workshop выполнено. Это **не** снимает HOLD с ART-UI, не меняет текущий Hidden Object и не разрешает реализацию FX.

## Что требуется от архитектора

1. Оцени **весь замысел и продуктовые четыре этапа**: ценность, зависимости, нестыковки, стоимость, риски; предложи обоснованные поправки. **Не расписывай подробно этапы 2–4:** их детали обсуждаются с Максом после каждого предыдущего этапа.
2. Подготовь **2–3 отличающиеся UX-гипотезы** и дешёвый способ сравнить их на **реально работающих простых эффектах**. На этапе 1 качество, сложность и число FX **не KPI**; зато каждый видимый элемент интерфейса должен иметь тестируемый материал/действие.
3. Предложи **детальную реализацию этапа 1**: scope, минимальные сцены/контролы, сравнение для Макса/Славы/Арианы, адаптация к доступному viewport браузера на 1920×1080, колесо по hover без фокуса, честный scroll/parameter separation, Undo/Redo, автосохранение с группировкой конфиг-снапшотов, галерея живых вариантов. Телефон — будущий view-only URL с монитором метрик и агентом вместо редактора, без QR-флоу.
4. Учти будущее, **но не строй сейчас**: FX-композиции, конструкторы сложных частиц и трейлов, агенточитаемые конфиги, возможную примерку на визуально верный игровой UI-лейаут, производительность и многоязычность. **Три фактических пользователя, не SaaS:** не придумывай массовую auth/roles/security-систему; базовую защиту не ломай.
5. Дай **одну карточку подготовки к запуску только этапа 1**, смету/срок/проверяемый результат и формулировку **WAIT FOR MAX GO**. Никаких автозапусков, назначений исполнителей и расходов до явной команды Макса.

**Очередность результата:** ревью общей программы → предложения по этапу 1 → архитектурные решения/оценки → карточка **READY / WAIT FOR MAX GO** → отдельное решение Макса. Если архитектор считает другое дробление более разумным, пусть объяснит его **продуктовую ценность**, не растягивая программу на бесконечные «минимальные MVP».
